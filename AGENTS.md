# AGENTS.md

Proyecto de grado: sistema de inventario para Salón de Belleza Zoom (FastAPI + PostgreSQL + Flutter + YOLOv8).
Todo el repo (código, comentarios, docs, commits) está **en español**; commits usan convención `feat:`/`fix:`/`ci:`.

## Arquitectura

- `backend/` — API FastAPI (async SQLAlchemy + Alembic). Entrypoint: `backend/app/main.py` (lifespan ejecuta `create_all` + seed al arrancar).
- `mobile/inventario_app/` — Flutter con **3 plataformas**: Android, Web (`flutter run -d chrome`) y Windows (`flutter run -d windows`).
- `backend/app/yolo/` — inferencia YOLOv8. Modelo `backend/app/models/best.pt` está gitignored (`*.pt`): sin él, `POST /api/inference/` devuelve 503 y `GET /api/health` responde `yolo_disponible: false` (esperado, S5–S6 pendientes). `InferenceService` es un singleton con carga perezosa.
- `backend/app/routers/reportes.py` — reportes y exportación real a **CSV y XLSX** (`openpyxl`), no CSV crudo. `/valorizacion` devuelve el inventario valorado a costo y a venta.
- Docs académicas en `tecnico y original/` y `revision-sistematica/` — **gitignored**, no editar desde aquí.
- `scripts/generar_*.py` — generadores de los 16 diagramas UML (PlantUML). Están **gitignored**: son material de trabajo local, no código del sistema. Se regeneran con `python scripts/generar_dcc.py` (etc.), requieren `plantuml.jar` + Java.

## Entorno de desarrollo (solo Windows)

El entorno activo es **100% local**, no Docker:

- **BD principal**: servicio de Windows `postgresql-x64-18` (PostgreSQL 18) en `localhost:5432`, BD `inventario_db`, usuario `admin_user`/`admin_password` (ver `backend/.env.example`); esquema canónico en `backend/app/db/inventario_db.sql`. pgAdmin 4 viene con la instalación de PostgreSQL.
- **`docker-compose.yml` usa el MISMO puerto 5432** con credenciales distintas (`zoom_user`): **nunca** correr la BD de Docker junto con la local. Docker queda solo como alternativa/respaldo; `scripts/backup.ps1` usa `pg_dump` de Windows (`C:\Program Files\PostgreSQL\18\bin`), no Docker.
- Lanzador único: `.\start-dev.ps1` (verifica PG, arranca backend + app). Flags: `-Web` (navegador), `-Windows` (escritorio), `-SinApp`, `-Detener`.
- Backend en local: `cd backend; .\venv\Scripts\Activate; python -m alembic -c alembic.ini upgrade head; uvicorn app.main:app --reload --port 8000`. El arranque también crea tablas y siembra datos (roles, categorías, marcas, admin). Para **celular físico** hace falta `--host 0.0.0.0` (si no, solo escucha en 127.0.0.1 y el celular no conecta).
- **El backend va en el puerto 8000** (puerto estándar de FastAPI). Si aparece ocupado, casi siempre es otro servidor local (por ejemplo Laravel Herd): identificar el proceso con `netstat -ano | findstr :8000`. Para no detener ese servicio, se puede levantar el backend en otro puerto y usar `--dart-define=API_BASE_URL=http://10.0.2.2:<PUERTO>` en la app.
- **Reiniciar el backend exige matar al worker, no solo al PID que escucha**: con `--reload`, uvicorn lanza un supervisor y un hijo `--multiprocessing-fork` que hereda el socket. Matar únicamente el PID que muestra `netstat` deja al worker sirviendo **el código viejo**: los endpoints responden 200 y los cambios no se aplican, lo que parece "el backend no se enteró". Localizarlo con `Get-CimInstance Win32_Process | Where-Object { $_.CommandLine -like "*app.main:app*" }` (más el hijo `multiprocessing-fork`, cuyo padre es el supervisor). Cuidado al filtrar procesos: si el filtro coincide con el propio PowerShell del comando, se mata a sí mismo. `--reload` sí detecta los cambios (`WatchFiles detected changes...`), pero tarda unos segundos: conviene comprobar que el efecto es real (por ejemplo, por el texto de un `detail` de error) antes de asumir que falló. Nunca matar el proceso del otro proyecto que escucha en `127.0.0.1:8000`.
- **La unicidad del nombre de una categoría no distingue mayúsculas.** `categorias.nombre` **no** lleva `UNIQUE` en la columna (en PostgreSQL ese UNIQUE distingue mayúsculas y permitía crear `Uñas`, `uñas` y `UÑAS` como tres categorías); la garantiza el índice `uq_categorias_nombre_lower` sobre `lower(nombre)`, igual que `uq_usuarios_email_lower` en usuarios. Está declarado en los cuatro sitios que deben coincidir: el SQL de referencia, el modelo (`app/models/categoria.py`), la migración `20260415_01` y la base viva. En el modelo la expresión va como `text("lower(nombre)")` y no como `func.lower(nombre)`: `__table_args__` se evalúa antes de que exista el atributo. `obtener_por_nombre` busca con `lower()` para que la reactivación funcione con cualquier capitalización, y `actualizar_categoria` excluye el propio `id` del chequeo para que renombrar solo por caja (`uñas` → `Uñas`) no se rechace a sí mismo. Las violaciones de unicidad que consigan colarse se traducen a **409 con mensaje en castellano** mediante el handler `IntegrityError` de `main.py`, no a 500.
- **psql desde PowerShell: cuidado con dos cosas**. (1) Un `-c` con varias sentencias se envía como una **única transacción**: si una falla, todas se revierten (salvó la tabla de `categorias` de quedarse sin UNIQUE). (2) Las cadenas con acentos se degradan a latin-1 y PostgreSQL las rechaza con "secuencia de bytes no válida para codificación UTF8". Para tocar `ñ` o tildes, escribir un `.sql` en UTF-8 y ejecutarlo con `-f`. Además `psql` pide contraseña de forma interactiva: exportar `$env:PGPASSWORD` antes o la llamada se queda colgada.

## Modo claro / noche

- La preferencia vive en `ThemeController` (`SharedPreferences`, clave `tema_modo`), **no** en la sesion del usuario: es una eleccion del dispositivo y tiene que sobrevivir a un cambio de cuenta. Por defecto arranca en noche, que es el aspecto que siempre tuvo la app. Se cambia desde el menu de usuario (⋮) de la barra superior.
- **El color sale del tema, nunca de un literal.** Para texto o superficies se usa la extension `AppPaleta` (`context.textoSecundario`, `context.paleta.stockBajo`, `context.paleta.negativo`), que devuelve el tono con contraste correcto en cada modo. Escribir `Colors.white70` o `Colors.orange` en un widget rompe el modo claro: el texto queda invisible sobre fondo casi blanco. `AppColors` queda solo como marca (morado) y aspecto del modo noche. `test/theme_test.dart` comprueba por codigo que todo par texto/fondo mantiene >= 4.5:1 en los dos modos, asi que un color nuevo mal elegido falla la suite.
- Excepciones justificadas a los colores literales: `barcode_scanner_page.dart` (el overlay de la camara tiene que seguir siendo oscuro en los dos modos para que se lea el encuadre) y el titulo y subtitulo del login, que van encima del degradado y por eso llevan blanco fijo. El degradado del login si cambia con el modo.
- **Al meter un color semantico dentro de un widget `const` hay que quitar ese `const`**, y no solo en la misma linea: el constructor contenedor puede abrirse ocho lineas mas arriba (`const Expanded(` ... `Text(... color: context.paleta.stockBajo)`). Quitar unicamente el `const` de la linea del color deja `Invalid constant value`.

## Peculiaridades de Flutter

- **Botones y campos: los tamaños grandes salen del tema, no de cada widget.** `theme.dart` fija mínimo 50 dp de alto y letra 16 para filled/elevated/outlined/text/segmented y ~62 dp de alto en los campos (contentPadding 16). No fijar alturas chiquitas por widget ni restaurar los `actions` pequeños de `AlertDialog`: en los formularios los botones van **a lo ancho dentro del contenido** (fila de `Expanded` con `minimumSize: Size(0, 50)`), porque los `actions` quedan diminutos y fuera del alcance del pulgar en el teléfono. Ejemplos: formulario de producto y diálogo de lote en `products_page.dart`.
- `pubspec.lock` está **gitignored** (poco común): siempre `flutter pub get` tras clonar.
- URL del API (`ApiConfig.baseUrl`), por prioridad: 1) valor guardado en `SharedPreferences` (`api_base_url`) desde el diálogo **"Configurar servidor"** (icono servidor en la barra superior y en el login) — sirve para cambiar la IP del PC **sin recompilar**; 2) `--dart-define=API_BASE_URL=...`; 3) default por plataforma (Android → `http://10.0.2.2:8000`, resto → `http://localhost:8000`).
- **Celular físico (no emulador)**: `10.0.2.2` no existe fuera del emulador. La PC usa IP fija **192.168.100.43** (DHCP deshabilitado en el adaptador Wi-Fi, `netsh interface ipv4 set address ... static`), el backend debe correr con `--host 0.0.0.0 --port 8000`, y el APK se compila con `--dart-define=API_BASE_URL=http://192.168.100.43:8000`. Si algún día cambia la IP, no hay que recompilar: se cambia desde "Configurar servidor" en la app.
- **`flutter run` contra el teléfono físico se cae con `Lost connection to device`** en cuanto el cable se desconecta o la pantalla se apaga: `adb devices` queda vacío y **no** es un fallo de la app ni del código. El APK ya quedó instalado, así que la app abre igual desde el menú del teléfono, pero sin hot reload ni logs. Antes de relanzar, comprobar `adb devices` y dejar la pantalla encendida (`adb -s <id> shell svc power stayon true`). El ciclo completo (Gradle ~45 s + instalación) se repite en cada relanzamiento: para cambios de Dart es preferible hot reload/restart desde la sesión viva.
- **Trampas del entorno al editar código**: el `edit`/`write` **no** matchea patrones multilínea contra archivos con finales **CRLF** (sí contra LF); convertir a LF o editar línea a línea. El repo es LF en el índice de git, así que convertir a CRLF ensucia el diff. En PowerShell, `$i:` dentro de `Write-Host` rompe el script ("referencia de variable no válida"): usar `("...{0}..." -f $i)`.
- Multiplataforma: la **cámara solo existe en Android/iOS**; web y escritorio usan selector de archivos (`kIsWeb`/`defaultTargetPlatform` en `detection_page.dart` y `shell_page.dart`).
- Importaciones condicionales — no romperlas:
  - `core/db/db_bootstrap.dart` (web, no-op) vs `db_bootstrap_io.dart` (desktop: sqflite FFI).
  - `core/services/local_db_service.dart` exporta `_web.dart` (memoria) o `_io.dart` (sqflite) según `dart.library.io`.
  - `core/utils/descarga_reporte.dart` exporta `_web.dart` (descarga por `<a download>`) o `_io.dart` (`path_provider` + `share_plus`) según `dart.library.io`.
- Plugins con código nativo: `mobile_scanner` (escáner de código de barras), `permission_handler` (permiso CAMERA), `share_plus` + `path_provider` (descargar y compartir el reporte exportado). El escáner **solo funciona en Android/iOS**: en web/escritorio el botón debe seguir ofreciendo el selector de archivos.
- AndroidManifest: el permiso `CAMERA` está declarado y `android.hardware.camera` va con `required="false"` para no romper la instalación en dispositivos sin cámara.
- `flutter run -d windows` requiere Visual Studio con carga "Desarrollo de escritorio con C++" (**no instalado** en esta máquina); `flutter run -d chrome` funciona sin nada extra.
- CI (`.github/workflows/build-mobile.yml`) analiza y compila APK en cambios de `mobile/`; tiene **Flutter 3.29 fijado** mientras el repo usa local 3.41.6 / `sdk: ^3.11.4` — verificar que el CI verde coincida antes de confiar en él.

## Backend — datos y migraciones

- Esquema de referencia: `backend/app/db/inventario_db.sql`. Las migraciones Alembic (`backend/alembic/versions/`, una cadena fechada `AAAAMMDD_NN_*.py`) deben reproducirlo exactamente: si cambia un modelo SQLAlchemy, actualizar el SQL **y** agregar una migración nueva (no reescribir `20260401_00`). Como el arranque ejecuta `create_all`, una migración que crea tablas debe saltarse las que ya existan (`has_table`, ver `20261101_01` y `20261111_01`).
- Backend con tests **pytest** en `backend/tests/` (mockean `AsyncSession`, no necesitan PostgreSQL): `python -m pytest`, o un archivo / `-k nombre`.
- `POST /api/inference/` acepta el campo Form `tipo_operacion` (default `entrada`): el reconocimiento registra **entrada** de stock; salida es trabajo futuro.
- `GET /api/health` responde `yolo_disponible`. Es la forma de distinguir "API caída" de "IA sin entrenar": el 503 de `/api/inference/` **no es un error de red** y la app lo muestra como "IA pendiente" (`ApiException` en `core/providers/inventario_provider.dart`), nunca como "sin conexión".
- CORS acepta cualquier puerto local (`localhost`/`127.0.0.1`) vía `allow_origin_regex` en `main.py` (el servidor web de Flutter usa puertos aleatorios).
- Los `Decimal` de los schemas Pydantic salen en JSON como **string** (`"8.00"`): en Flutter parsear con `parseDouble` de `core/models/json_utils.dart` (nunca `as num`, truena en runtime y cae al catch "sin conexion").
- `dataset/` (imágenes YOLO) y `backups/` (SQL dumps) viven en la raíz; ambos están gitignored.
- **`MissingGreenlet` al serializar**: `UsuarioService.to_out()` lee `usuario.rol`, una relationship *lazy*. Accederla fuera del greenlet de SQLAlchemy async lanza `MissingGreenlet` y el endpoint responde 500 **aunque el INSERT ya se haya hecho** (por eso quedan usuarios a medias con el rol por defecto). Por eso `to_out` es `async` y consulta el rol explicitamente, y `UsuarioRepository.crear()` relee con `obtener_por_id()` en vez de quedarse con `db.refresh()` (que recarga columnas pero no la relationship). El resto de metodos del repositorio ya usan `joinedload(Usuario.rol)`.
- **La sesion usa `expire_on_commit=False`**: tras un commit los atributos **no** se invalidan y un `joinedload` posterior **no** sobrescribe una relationship que ya estaba cacheada. Al cambiar el `rol_id` de un usuario, el `PUT` respondia `200` con `rol_id: 1` y `rol_nombre: "vendedor"`. `UsuarioService._rol_cargado()` solo reutiliza la relationship cacheada si su `id` coincide con el `rol_id` actual; si no, fuerza la consulta.
- **No acceder a una relationship lazy desde codigo sincrono** en una app async. Patron: comprobar con `__dict__.get("rol")` si ya esta cargada (eso no dispara IO) y, solo si falta, consultarla con `await`. Si se consulta siempre, `listar()` se convierte en N+1.
- **Precios obligatorios y mayores a 0**: `ProductoCreate` exige `precio_compra` y `precio_venta` con `Field(gt=0)`; un producto sin precio real falsea la valorizacion del inventario, asi que ya no se admite 0 (antes `precio_compra` era opcional y quedaba en 0). `stock_minimo` si admite 0 (`ge=0`), que significa "sin alerta de stock bajo". La app valida lo mismo en `core/utils/validaciones.dart` antes de llamar al API, para que el error se vea en el campo y no como un 422.
- `GET /api/usuarios/` devuelve **activos e inactivos** a proposito: la app los separa en Total/Activos/Inactivos y permite reactivarlos. El listado de catalogos (categorias, marcas, proveedores) si devuelve solo activos.
- **Sesión vencida y renovación**: el token dura `ACCESS_TOKEN_EXPIRE_MINUTES` (8 h) desde que se emite. Al abrir la app, `AuthProvider.tryAutoLogin` lee el `exp` del token guardado (`core/session/token_jwt.dart`) y, si venció, borra la sesión y muestra el login con "Tu sesión expiró". En uso, `ApiClient` avisa por `ApiClient.alSesionVencida` ante cualquier `401` (salvo `/api/auth/login`, donde es contraseña incorrecta, y `/api/auth/renovar`), y `AuthProvider.sesionVencida` vuelve al login **una sola vez** aunque fallen varias peticiones juntas. Cuando al token le queda < 1 h, tras una respuesta correcta `ApiClient.alRenovarSesion` dispara `POST /api/auth/renovar`, que relee al usuario (403 si lo desactivaron, rol actualizado) y entrega un token nuevo: quien trabaja no es expulsado a mitad de turno. Antes, con el token vencido la app seguía "abierta" con todo vacío. `test/sesion_test.dart` cubre los casos.
- **Sin timeout explicito, la app se ve colgada**: `package:http` espera al timeout del sistema y con el backend caido el usuario tarda varios minutos en ver el error. `ApiClient` define `timeoutPeticion` de 12 s para lo normal y `timeoutSubida` de 2 min para la deteccion por imagen (sube el archivo y el backend carga el modelo YOLO). Con el servidor apagado el telefono da `Connection timed out` (el firewall descarta los paquetes), no `Connection refused`.
- **Reconexion con el backend**: `ConnectivityService` (connectivity_plus) solo sabe si el **telefono** tiene red; cuando la laptop se suspende el telefono sigue con Wi-Fi, asi que ese evento no dispara y la app no se enteraba de que el servidor habia desaparecido. Lo cubre `ServidorController` (`core/providers/servidor_controller.dart`), que pregunta a `ApiConfig.salud` (`/api/health`) cada 15 s y al volver del segundo plano, y avisa por `onReconectado` para recargar el inventario. `ServidorGuard` (`shared/widgets/servidor_guard.dart`) se monta en `MaterialApp.builder`, observa el ciclo de vida (comprueba al `resumed`) y muestra una franja "Sin conexion con el servidor" con boton Reintentar. `iniciar()` (el timer) se llama **solo** en `main()`: los tests no deben dejar un timer vivo o `pumpAndSettle` no termina. `test/servidor_controller_test.dart` cubre las transiciones con un `MockClient`. Para que la laptop no desaparezca: `powercfg /change standby-timeout-ac 0` (nunca suspender con corriente) y el ahorro de energia del Wi-Fi en maximo rendimiento.
- **Categorías: el borrado es lógico y el nombre es `UNIQUE` sobre toda la tabla.** `DELETE /api/categorias/{id}` marca `activo=false` (para no dejar productos con categoría huérfana) y `GET /api/categorias/` devuelve solo las activas. Como la fila desactivada sigue reservando el nombre pero es invisible, crear una categoría con el nombre de una desactivada **la reactiva** en lugar de crear otra fila. `PUT /api/categorias/{id}` renombra y solo choca con nombres de categorías **activas**.
- **Validaciones de formularios**: viven en `mobile/inventario_app/lib/core/utils/validaciones.dart` (`Validaciones`), compartidas por todos los formularios para que la regla sea la misma en alta y edición. Los nombres de persona/categoría/marca/proveedor no admiten números; el de **producto** sí (talles, ml, tonos) pero exige al menos una letra, para que "123" no pase. Los precios exigen `> 0`. En movimientos, entrada y salida exigen `> 0` y el ajuste admite `0` (fija el stock exacto); una **salida mayor al stock** se rechaza con `400` (`No hay stock suficiente: disponible N`) en `routers/inventario.py`, en vez de recortarse en silencio a 0 como hacía `max(0, ...)` en `movimiento_repository.py`. `test/validaciones_test.dart` cubre las reglas. **El mensaje del validador se pinta como `errorText` del campo, y Flutter lo corta a una línea con elipsis**: los campos con mensajes largos (precios, cantidad de movimiento, nombre, correo) llevan `errorMaxLines: 2` en su `InputDecoration` o el texto sale como "No hay stock suficiente: disponibl…".
- **Movimientos por lote (HU-16 / RF-24)**: `POST /api/inventario/movimientos/lote` registra varios productos **del mismo tipo** en una sola operación con guardado **todo o nada**: valida las filas del lote antes de tocar la BD y, si una falla, responde `400` con una línea por fila rechazada (`Fila 2 (Esmalte Rojo 30): no hay stock suficiente: disponible 3`) y no guarda ninguna. El núcleo vive en `InventarioService.registrar_lote()` para reutilizarlo desde la detección IA (RF-10, con `origen="ia"` y `sesion_id`); el endpoint manual entra con `origen="manual"`. Rechazos cubiertos: fila repetida, producto inexistente y producto dado de baja, todos con mensaje claro y número de fila. El ajuste admite cantidad `0` (fija el stock exacto), por lo que el CHECK es `(cantidad > 0 OR tipo = 'ajuste')` y está sincronizado en tres sitios: `inventario_db.sql`, el modelo `Movimiento` y la migración `20260401_00`. En la app, el diálogo de movimiento de `products_page.dart` acumula filas (con producto dropdown por fila, validación de duplicados y quitar fila) y muestra el detalle multi-línea del backend; `InventarioProvider.registrarLote` **no** captura `ApiException` para que el detalle fila a fila llegue completo al diálogo. Entradas: el botón "Movimiento por lote" de la barra superior de productos (sin fila precargada) y la tarjeta de cada producto (fila 1 ya cargada, con la cantidad replicada en la alerta de stock bajo). `test/product_service_lote_test.dart` cubre el payload y el rechazo fila a fila vía `MockClient`.
- **Registrar venta (`features/ventas/presentation/sales_page.dart`) es una pantalla de teclado.** El producto se busca por **Código** = columna `producto.sku` (código propio de la tienda, se carga en el formulario de productos); si no coincide, prueba con `codigo_barras` para que funcione un lector. Descripción, P. público, P. mayor y Saldo son de solo lectura (`InputDecorator`, sin foco, fondo distinto). Flujo: Código → Enter → Cantidad → Enter → Monto → Enter agrega la fila y vuelve a Código; Enter con Código vacío o Ctrl+Enter registra; Esc limpia la captura. Lo decide `_alEnter()` según el campo enfocado (lo usan el teclado físico y la acción del teclado del celular): antes cualquier Enter registraba la venta, y un lector de códigos de barras (que manda Enter) cobraba cada escaneo. Código inexistente + Enter avisa y no avanza. `test/sales_teclado_test.dart` cubre el flujo. El **monto total de la línea es editable**: se envía como `total_linea` y el backend lo acepta si coincide con `cantidad × precio_unitario_negociado` dentro del redondeo a centavos (`_total_linea` en `venta_service.py`). Pago con checkboxes Efectivo/QR (ambos = pago mixto con monto en efectivo y el resto por QR). Doble registro: guardia síncrona `_guardando` (el botón deshabilitado no frena el Enter) más `clave_idempotencia`; tras registrar se limpia toda la página. `producto.precio_mayor` (opcional, `> 0`) está en el SQL, el modelo y la migración `20261028_01`; en venta mayorista se usa como precio de lista.
- **Sucursales (HU-1)**: catálogo de productos **único**, stock **por sucursal** (`inventario` es una fila por `(producto_id, sucursal_id)`, `uq_inventario_producto_sucursal`). `movimiento`, `venta` y `compra` llevan `sucursal_id` obligatorio. La sucursal de cada petición la resuelve `get_sucursal_activa` (`app/core/sucursal.py`) desde el encabezado `X-Sucursal-Id`, **solo para el administrador**: al vendedor se le ignora y opera siempre en la predeterminada (`configuracion_sistema`, una sola fila `id = 1`). La predeterminada no se puede desactivar. En la app, `SucursalController` (`core/providers/`) guarda la sucursal activa hasta cerrar sesión, `ApiClient` manda el encabezado y `SelectorSucursal` (barra superior) la cambia. Los reportes y los listados de ventas/compras aceptan `?sucursal_id=` (sin él, todas; el stock se suma). El **costo promedio de compra** pondera el stock de **todas** las sucursales, porque `precio_compra` es uno por producto. Fuera de alcance por ahora: caja, gastos, sueldos y el reporte financiero siguen siendo globales.
- **Razones de movimiento (HU-3)**: `razon_movimiento` (por tipo), obligatoria en **todo** movimiento. Las de `sistema = true` (venta, compra, anulación de venta, stock inicial, detección IA, ingreso por traspaso, "Registro previo" para el histórico) las asigna el backend con `razon_sistema(codigo)`, una subconsulta asignada a `razon_movimiento_id` para no gastar un SELECT; no se listan en el formulario ni se editan. La razón con `requiere_sucursal_destino` ("Salida a sucursal") es un **traspaso**: el servicio registra la salida (`confirmar=False`) y la entrada en el destino en la misma transacción, y `sucursal_relacionada_id` apunta a la otra punta. Se administran en la página **Configuración** (solo admin), junto con sucursales y predeterminada.
- **Cantidad inicial (HU-2)**: `ProductoCreate.cantidad_inicial` (≥ 0, default 0). Si es > 0, el alta crea el inventario y una entrada "Stock inicial" en la sucursal activa, en la misma transacción que el producto.
- **Diálogos con `autofocus` y `Column` sin scroll → franja amarilla `BOTTOM OVERFLOWED BY N PIXELS`.** El teclado sube al abrir el diálogo y resta alto; si además aparece un mensaje largo, el contenido no cabe. El caso real es `shared/widgets/server_config_dialog.dart`: el `TextField` tiene `autofocus` y el mensaje de "No se pudo conectar. Revisa la IP…" ocupa tres líneas, así que el diálogo se desbordaba al abrirse el teclado. La franja es un **desbordamiento de layout**, no un error de Dart: no confundirlo con los `Unhandled Exception` de consola. Se corrige envolviendo el `content` en `SingleChildScrollView`, como ya hacen el formulario de producto y el diálogo de proveedores.

## Qué se versiona y qué no

El repositorio lleva **solo el código del sistema**: `mobile/` (app), `backend/` (API), `scripts/*.ps1` (operación: backup, deploy, `start-dev.ps1`), CI y docker-compose.

Quedan fuera (`.gitignore`, material de trabajo local): documentos del proyecto de grado (`tecnico y original/`, `revision-sistematica/`), generadores de diagramas UML (`scripts/generar_*.py`), hojas de cálculo y documentos de Office (`*.xlsx`, `*.docx`, `*.csv`), fuentes PlantUML (`*.puml`), pesos del modelo (`*.pt`) y resultados de entrenamiento (`runs/`).

Excepción deliberada: `README.md` y `AGENTS.md` **sí** se versionan (regla `!README.md` / `!AGENTS.md` en `.gitignore`), porque son la documentación del código. Si agregas un documento nuevo de trabajo, no lo versiona — esa es la intención.
